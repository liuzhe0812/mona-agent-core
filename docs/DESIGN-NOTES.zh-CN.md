# 长期设计方案与本轮讨论沉淀

> 第1—13节保留早期v0.1设计背景；当前实现范围以v0.3架构、迁移文档和文末修订为准。不能把历史“未实现”直接当作当前清单。

> 版本提示：第1—13节保留最初设计依据；其中“v0.1”是历史实现边界，不代表v0.2仍缺失相同能力。当前架构以 ARCHITECTURE.zh-CN.md 为准；本轮决定追加于第14节。

## 1. 为什么保留这份文档

这不是聊天逐字稿，而是把本轮讨论中需要长期参考的概念、取舍、约束和修正固化下来。以后新增 Memory、Planner、Code、MCP 或 UI 时，应先判断它们属于哪一层，而不是不断给 Runtime 增加特殊分支。

当前目标明确为 **Rust 的可复用最小 Agent Core**。此前已有 Python Agent 的背景不是本项目继续引入 Python/Node 的理由；同样，本项目也不意味着已有业务已迁移完成。

“源码已写出”“能够编译”“测试通过”“真实服务联调完成”“生产验收通过”是五个不同阶段，必须分别记录。

## 2. 概念底座

### 2.1 Agent 不等于 ReAct

Agent 的关键是围绕目标进行决策、行动并利用反馈。ReAct 是其中一种运行范式，不是全部 Agent 的必要定义。本项目选择它作为默认基座，是因为它足以构成一个可扩展的单任务执行器。

同样，不能把“所有 Multi-Agent 的每个成员都必须采用 ReAct 或 Plan-and-Execute”当成定理。多智能体是组织方式；成员可能是自主循环、固定工作流、一次模型调用或其他受控执行组件。

### 2.2 ReAct 与 Plan-and-Execute 可以组合

ReAct 可以直接完成一个完整任务，不只处理“一个微观动作”。Plan-and-Execute 显式分离规划和执行；其中每个步骤可以用 ReAct，也可以用确定性函数。

因此，“ReAct 只能微观、Plan-and-Execute 必然更擅长复杂任务”过于绝对。拆层是本项目的工程选择，不是能力排行榜。

本项目采用：上层 Planner 拆任务，下层 Core 执行任务。Planner 不是通过一个万能 Hook 任意接管内部循环。

### 2.3 模型决定，程序执行

模型生成工具调用请求；Runtime 校验、授权、调度真正的函数／进程／API；结果再进入下一轮上下文。模型返回调用对象，不等于动作已被执行。

后续模型请求一般包含系统约束、当前目标、需要的历史 assistant 工具调用及对应结果，不是只把上一次文本发回去。上下文压缩可以改变投影，但不能破坏调用／结果协议。

不要求模型显式返回 `Thought` 字段。原始 ReAct 的可读推理格式与现代工具调用协议不是一回事；也不能假设所有模型都会或应该把隐藏推理交给 Runtime。

### 2.4 Function Calling 与 Tool Calling 的准确关系

两者在很多 API 和工程讨论中高度重叠。Tool Calling 是更通用的名称，Function Calling 常指其中的函数型工具协议。不能简单分成“前者只能做简单函数，后者才能做复杂 Agent”。

工具可以包装一个函数，也可以包装复杂服务。对 Core 来说，重要的是统一的能力契约，而不是内部有几个函数。

### 2.5 Tool 不只是改名

最低限度包括名称、用途描述、参数结构和执行入口；交付版本还要约定结果、错误、取消、进度、并发安全性和副作用声明。

LLM 只看到可选择的能力描述；宿主始终拥有最终执行权限。Schema 约束参数形状，不证明调用正确、授权充分或操作安全。

## 3. Core 的长期边界

Core 的任务是：在明确权限和资源限制内，完成一次可观察、可取消、状态清楚的执行。

固定保留：

- 执行状态与 ReAct 闭环。
- 模型／工具协议，调用与结果关联。
- 可替换模型适配器和工具执行入口。
- 当前运行上下文与投影的分离。
- 有界事件、取消、超时、步骤和模型调用限制。
- 插件装配与少量稳定扩展点。

不默认放进 Core：长期记忆数据库、向量检索、自动规划、多智能体团队、业务工具、Skills 内容、MCP 客户端、Cron、UI、工作区和渠道接入。

短期运行状态不应被错误地挪成“可选 Memory 插件”；没有当前任务记录，默认循环无法正确运行。真正可选的是跨任务记忆能力。

## 4. Pi 与 DSH：借鉴思想而非绑定实现

### 4.1 从 Pi 保留的设计方向

重点是 Agent 状态、消息投影、结构化模型／工具接口、事件、取消及轮次安全边界。官方 agent-core 文档明确展示了内部消息到模型消息的转换链和工具执行事件，参见 [参考来源](REFERENCES.md)。

我们的取舍不是机械移植其类和所有选项：不引入 TypeScript Runtime，不承诺插件兼容，不把 Coding Agent 应用能力一起塞进 Core。

### 4.2 从 DSH 保留的设计方向

重点是服务定义与实现分离、显式依赖、组合根、作用域所有权、可撤销注册和生命周期。DSH 的官方架构把模型、工具、会话和循环都描述成插件服务；本项目采用更小的装配集合，不实现完整 Cordis。

尤其保留“先定义服务协议，再由插件提供实现，再由消费者使用”的方向，避免 Memory 插件导入 Runtime 的私有类。

### 4.3 保持可交付的克制

不因为 DSH 有完整插件框架，就顺手增加配置表达式、动态热替换、插件下载、包管理、UI 注入、分布式发现和动态作用域树。

v0.1 的插件是可信 Rust crate，在启动时注册；依赖检查、服务冲突检测与初始化失败回滚是真正需要的部分。模型服务可由插件提供，默认驱动仍是 Core 的标准实现。

### 4.4 nanobot 的参考地位

此前讨论过 Provider 解耦、工具注册、轮次限制、结果规范化、Session 与执行分离，以及错误处理。这些仍是有价值的工程检查项。

但本次交付没有重新核对 nanobot 的完整源码，不把此前对具体类名、代码行数或“生产级错误恢复”的描述作为本项目已验证能力的证明。本轮实现主要沿用 Pi 与 DSH 的架构边界，不移植 nanobot 代码。

## 5. 插件标准化的真正含义

### 5.1 不是给每个功能各造一个 Hook

通用接入方式足以覆盖大多数能力：服务发布、工具注册、上下文变换、结果变换、权限否决、事件观察。具体插件可以组合多个入口。

### 5.2 扩展点必须有语义

每个入口必须明确：何时执行、输入是否只读、输出怎样提交、执行顺序、超时、失败是否影响任务、关闭时如何清理。

ContextTransform 和 ResultTransform 是关键链路，失败停止当前运行；ToolPolicy 异常必须拒绝执行；EventObserver 是非关键观察，失败不改变结果。不能混为同一种“任何异常都忽略”的 Hook。

### 5.3 状态有唯一提交者

插件获得独立投影和只读上下文，返回结果给 Core；不得直接修改运行历史、伪造工具成功或绕过最终权限检查。ResultTransform 的 call_id 和 status 是不可改的执行事实。

### 5.4 服务注册可撤销不等于业务动作可撤销

关闭时可以撤销工具入口、事件监听和服务注册，但不能自动撤销已写入的文件、已发出的 API 或已修改的数据库。

已经交给外部代码的 Arc 也不能魔法撤回。v0.1 的撤销指 Host 不再接受运行并移除注册表，不是内存引用权限系统。

### 5.5 原生插件不是沙箱

Rust 类型安全和禁止本项目 unsafe 不等于第三方插件没有权限。可信进程内代码可以直接访问网络、文件甚至自己创建线程。运行时服务视图和预算网关减少误用，不构成对恶意代码的强隔离。

未来需要不可信插件时，应单独设计进程或 WASM 宿主、权限、资源限额、协议版本、可取消执行和升级策略；不要直接加载不稳定 Rust ABI 的动态库。

## 6. Memory 的长期方案

Memory 属于跨任务状态扩展。检索结果通过 ContextTransform 注入，保存行为可以通过显式工具或未来的可靠结束提交实现。

v0.1 示例选择有界内存后端 + 显式写入工具，不自动把每次对话写入“长期记忆”。这是为了避免误存秘密、用户未授权的偏好以及把随口输入变成永久规则。

后续可以替换 MemoryBackend 为文件、数据库或向量后端，但不应改变主循环。检索的数据始终是参考资料，不应提升为系统级权限或自动授权依据。

若引入“任务结束后必须可靠落库”，不能把它实现为可丢事件的 EventObserver，需要可等待、可失败的提交协议。本文明确保留这个未来扩展要求，v0.1 不假装已有事务式记忆持久化。

## 7. Planner 的长期方案

计划生成、步骤状态、重新规划、依赖排序属于上层编排。每次子任务执行仍使用统一 AgentExecutor；它们不是另一套模型／工具 Runtime。

v0.1 实现：模型生成 JSON 计划 → 计划结构与长度校验 → 顺序执行步骤 → 收集有限的前序结果参考 → 遇到失败停止。

规划阶段禁用工具，避免“只让它规划”却发生实际操作。规划和执行都共享同一个 TaskControl。

尚未实现自动重新规划、并行 DAG、用户审批计划、检查点和跨进程恢复。后续每一项都应说明怎样继承预算、权限与取消，不得让 Planner 成为绕过限制的后门。

把一张计划表注入提示词，和拥有步骤调度器的 Plan-and-Execute，不是同一种能力；文档与产品界面应区分。

## 8. 长结果与 SoL-Pi 式优化的设计沉淀

以下记录的是这轮讨论中值得保留的优化思路，不是对某个上游最新版本的逐项功能认证。

### 8.1 确定性动作链可以下沉

例如“写文件后运行指定验证”可以封装成一个工具能力，减少必须由 LLM 决定的回合。它不意味着 Runtime 可以自行追加未授权的危险动作。

### 8.2 Tool Result 不必完整反复塞进上下文

长日志可保存到应用控制的存储，模型只拿必要片段、摘要和定位符，需要时通过读取工具恢复。存储和读取能力必须一起设计；只有一个 handle 字段不构成完整方案。

### 8.3 Reducer 是可选调用，不是最低依赖

压缩日志可以用另一次模型调用，使用同一个模型也可以，不必强制独立部署另一台“reducer 服务”。关键是这次调用的预算、权限、证据与失败回退。

摘要模型可能错误，因此保留的证据片段要可与原始内容核对。文字片段可核对不等于模型的所有总结解释都正确。

v0.1 没有 reducer；先用结果变换接口与有标记截断。未来加 reducer 时必须经过 RunContext.model，不能产生不计费／不受限的辅助请求。

### 8.4 上下文压缩不等于删除执行记录

压缩进入模型的投影，尽量保留可追踪的执行事实；在步骤边界处理，不打断尚未配对的工具调用。压缩触发还应考虑上下文压力、恢复成本和模型缓存行为，不能默认“越频繁越省钱”。

## 9. 可靠执行的底线

### 9.1 不完整调用绝不执行

文本增量可以显示为暂态；工具参数必须等待完整 JSON、合法结束原因和干净的传输结束。遇到 length 或缺少 [DONE] 时，不能把看起来已经完整的参数当成执行许可。

### 9.2 失败、取消、超时和未知结果要分开

取消是停止意图，超时是没有在期限内获得确认，二者都不证明远端没有发生动作。已启动工具若无法结算，要保留 Unknown，而不是 Success 或“已撤销”。

### 9.3 不盲目重试

同一个 Tool Call ID 的重复提交会被识别，但这不等于数据库级 exactly-once。模型可以用不同 ID 请求同一个动作；崩溃恢复也可能重新提交。幂等键、状态查询和事务策略必须由具体工具或持久化层设计。

v0.1 不自动重试模型和工具，以可解释性换取部分可用性。未来只有在错误可判定、没有产生不可重复副作用、没有对外提交不一致增量时，才讨论受限重试。

### 9.4 串行默认、明确并行

工具默认独占。读操作并不天然无冲突，例如它可能读取正在变化的共享工作区；ParallelSafe 是工具作者对后端语义的声明，不是 Runtime 通过名称猜测出来的结论。

### 9.5 基础限制不能变成可选装饰

轮次、时间、并发、消息／响应／审计长度及模型调用限制属于 Core。具体权限规则可替换，但最终关口不能被一般中间件放宽。

## 10. 事件、审计与持久化分层

实时观察流允许消费变慢或掉事件；它服务 UI 体验。最终结果通道服务调用者取得运行结论。需要耐久保证的 Session／审计服务需要独立提交机制。

三者不能混为一条无限消息列表。把所有事件写入同一个无界数组既增加内存，也无法解决进程崩溃和一致性。

v0.1 的 RequestAudit 保留规范化模型输入，仍不是 DSH 全量 Session 投影／持久化系统。后续要加持久化，应先定义版本、提交点、完整性、恢复时的未知外部动作，以及是否允许继续执行。

## 11. 可复用方式：Core、Runtime、Server

Core 本身包含 Agent Runtime，即执行循环。Tokio runtime 是运行异步 Rust 任务的调度环境，概念不同。

业务可以直接链接 Core。WebUI 并不要求 Core 内置 HTTP 服务；可以由薄应用层把 start、cancel、events、result 映射为 HTTP／WebSocket。

Tauri 等 Rust 宿主可以直接复用库。Python 应用未来可以选 FFI 或 IPC，但应保持 Agent 执行逻辑只有一份；桥接层不是再实现一个 ReAct 循环。

是否制作标准 agent-server 取决于是否需要独立部署、多语言调用、身份认证与服务治理。它应是单独应用包，不进入最小 Core 的默认依赖。

## 12. 高性能目标应怎样落地

先保证不会无限积压、不会重复复制无穷长日志、不会每个请求重建 HTTP 客户端、不会无限并行和失控重试。再基于基准测量进行优化。

Rust 可以帮助控制本地内存、并发和框架开销，但不能缩短远端模型本身的推理过程，也不能自动减少需要的 token。

当前存在有界克隆、trait object、async-trait 装箱和 JSON Value 解析，属于第一版可维护性的取舍。没有性能测试数据以前，不给出吞吐倍数、延迟下降比例或最低内存承诺。

## 13. 交付门槛与演进顺序

优先顺序建议：

1. 在真实 Rust 环境完成格式化、构建、单测、集成测试，生成 Cargo.lock 并记录工具链。
2. 用准备交付的真实模型端点验证流式、错误、工具参数和取消；按最终 OS 验证。
3. 做故障注入、工作区副作用工具验证、权限与敏感日志审查。
4. 在内核稳定后添加持久化、原文归档、MCP、自动规划增强等扩展。
5. 根据真实负载做基准与资源预算优化。

不要用“只有多少行”代替测试，不要用“参考了开源框架”代替验证，也不要为了未来可能有的功能一次性实现通用插件平台。

本项目长期保持的原则是：**固定协议与执行约束，扩展能力与策略。最小不是缺少必要保障，而是不把业务产品的所有功能塞入内核。**


## 14. v0.2：统一应用层与可选双桥接

### 14.1 先统一业务调用，不统一所有网络框架

开始任务、停止、追加输入、取结果和订阅是同一套应用行为。Application保存任务句柄、幂等与回放；Tauri/HTTP分别只处理自己的参数、鉴权/权限边界和传输。一个共享Application可以供两边使用，不在桥接里再造ReAct。

### 14.2 “Rust API”不是“HTTP API”

agent-api是库接口。Tauri本地UI走IPC/Channel，HTTP只在浏览器/远程部署时需要。保持Core不认识Tauri/Axum；桥接不需要知道具体Engine和模型厂商。CLI可以完全绕过Application直接嵌入Core。

### 14.3 流式是状态协议，不是打字动画

借鉴Codex的工作项ID、开始/完成和权威终态。增量供即时展示，完成项覆盖旧状态；参数生成不等于工具开始执行，输出日志不等于最终结果。失联和慢消费后要恢复状态，不是继续盲拼剩余token。

### 14.4 有界回放，不假装耐久日志

Core状态/事件同序提交；Application保留小窗口journal。过旧游标收到带序号的snapshot，丢弃本地过时投影。UI有界预览与裁剪标志，不能用一条无限列表保存所有日志。崩溃恢复和持久化幂等仍另设协议。

### 14.5 Tauri也需要背压

直接无限send到Channel不能解决慢JS。逐包ACK让桥接只保留一个在途消息；订阅丢弃或超时不应取消共享任务。HTTP按需读取，同样使用统一恢复语义。

### 14.6 扩展点服务业务，但不放开控制权

工具可提供coding.diff等命名空间详情，供业务UI渲染；不允许其伪造其他Run、改写状态或跳过授权。计划、多任务、审批仍需独立业务协议，不因为想画一张卡片就让插件随意修改Core内部对象。

### 14.7 JEV暂缓

用户决定先不为JEV修改核心架构。本版没有新增评估模型接口、JEV专用策略或第二个循环。未来需要时根据真实用例提出ADR，而不是提前加入尚未使用的抽象。

### 14.8 核心不是从0.1开始永不修改

此次RunHandle外移和流式协议升级是补齐通用语义，采用API版本升级处理。目标仍是后续业务扩展不侵入内核，而不是保证一版接口永远满足所有需求。


## v0.3 修订：从业务项目发现通用缺口，而不是吞并业务

Mona已有能力是验证样本，不是Core需求全集。此次只补内容/结果协议、工具选择、可靠记录提交时点和模型协议保真；数据库、会话、Office、MCP实现、工作流和Python桥接仍在外部。

之前“检查点将来需要接口”的缺口，本版通过可选CheckpointSink实现；仍没有存储产品和自动恢复。之前纯字符串消息已扩为Content，私有协议回传与UI展示分开。按需工具是从冻结注册表选择视图，不是实现热加载框架。

既不能把“插件优先”理解成永不修正公共契约，也不能用“主流框架也有”作为无限加功能的理由。新增能力必须证明跨业务用途和必要的执行时点，并有默认不启用的简单路径。

最终原则仍是：固定协议和执行约束，扩展能力与策略。UI桥接、通用Application和Core可以独立选用；Rust API升级不必强迫UI协议跟着破坏性改变。JEV继续不进入本次架构。
