# 可等待检查点：协议与失败语义

## 1. 它是什么，不是什么

CheckpointSink 是可选的、被执行器等待的快照提交接口。它不是Session数据库、恢复引擎、审批服务、事件总线或业务事务管理器。默认不安装，Core不访问磁盘。

注册方式：宿主HostBuilder.checkpoint_sink，或插件Registrar.checkpoint_sink。每个Host最多一个sink；重复注册报错。需要多个持久化目的地时，由外部sink统一说明原子性/成功条件，Core不假设多个后端能组成事务。

## 2. 快照内容

RunCheckpoint 包含独立版本号、run_id、单Run递增revision、执行阶段、step、canonical transcript、pending_tools、本轮工具名、模型选项、可信metadata、用量及可选终态/错误。

phase在JSON中是带phase判别字段的对象。revision是执行状态提交序号，不是token序号或UI事件序号。快照用Arc持有独立数据，后续执行不会修改已交给sink的对象。

工具批次期间，transcript可以有尚未配对的assistant调用，已完成的局部结果保存在pending_tools。它不是可以直接发给模型的messages；只能在全部调用有结算结果后形成完整协议历史。

不保存Tokio Future、数据库连接、插件内存、UI全部增量或完整原始HTTP报文。工具集合仅记录本轮名字，不序列化工具实现。原始请求审计仍是独立的有界内存记录。

## 3. 提交时点

| 阶段 | 必須确认后才继续的动作 |
|---|---|
| BeforeModel | 本轮主模型调用 |
| InputApplied | 接纳队列输入并返回applied回执 |
| AfterModel | 主模型完整消息入记录之后、实际工具派发之前 |
| ToolIntent(call_id) | 进入该工具函数之前 |
| ToolSettled(call_id) | 已知结果/未知结算经治理后，进入后续控制流程之前 |
| AfterTools | 整批规范化结果按调用顺序加入历史，进入下一轮之前 |
| RunFinished | 发布最终成功结果与run终态之前 |

同一Run的commit严格串行，工具函数本体不在存储锁内执行；不同Run可以并发调用同一个sink。并行工具结束顺序不固定，revision记录实际提交顺序；最终历史仍按模型调用顺序。

Schema/权限预检拒绝的工具没有进入函数，不记录ToolIntent；其结果在AfterTools/最终快照提交。已接受但尚未实际派发的调用失败时保留Skipped。部分并行结果通过ToolSettled保存，不要求等整个批次结束才写。

BeforeModel只指默认主循环。ContextTransform中的辅助模型调用仍走预算网关和RequestAudit，但没有额外自动建立一套检查点循环；插件自己执行的外部动作不在Core调度保证内。

## 4. 确认与失败

sink返回Ok，表示它按自己文档中的成功条件接纳了这个精确快照。内存sink不能声称已落盘；数据库sink应在事务提交等条件完成后再返回。

第一次确认失败、超时、panic或快照超限会锁定该Run的检查点错误，不自动重试，也不尝试绕过它继续发起新模型/工具动作。存储错误内容统一脱敏。已经派发的并行工具按取消语义收尾，不能逆转外部事实。

- 派发前失败：该工具不执行。
- 结果提交失败：工具可能已经成功，保留已知Success/Error，Run失败；不重做工具。
- 正常终态提交失败：不向调用方返回Completed，RunReport.checkpoint记录失败和最后确认revision。
- 原本已取消/超时/失败时终态提交失败：保留原始停止原因，同时在checkpoint状态另记存储失败。

如果后端完成写入但确认丢失，Core不能断言没有提交。外部sink应以自己的命名空间加(run_id,revision)实现幂等，检查重复提交的内容一致性；应用负责持久化命名空间、跨实例ID策略和查询。

## 5. 取消与期限

检查点是结算操作，使用独立的短期取消令牌与checkpoint_timeout；不沿用一个已被用户取消的令牌，否则终态永远无法保存。调用前后的工具派发边界仍重新检查任务取消/期限，不因成功提交intent而越过停止要求。

默认每次提交最多5秒，再加cancellation_grace。多个待结算调用可能使关闭耗时累计超过一个提交期限；Host.shutdown可能返回排空超时并保留资源，宿主需等待/重试关闭。不是“点停止后立刻杀进程”。

执行器选定终态后的取消不能撤销已经完成的工作；若终态提交已在进行，应以最终报告为准。所有取消仍是合作式，原生不让出执行权的插件不能被此接口强杀。

## 6. 容量与成本

max_checkpoint_bytes默认8MiB。提交的是完整快照而不是WAL差量，适合第一版明确语义；有序复制、序列化和存储IO都产生开销。没有性能基准，不宣称“持久化零开销”。

超限时明确失败，不对canonical history静默截断。高负载后端可存外部附件、选取适当预算或在sink内部做版本化增量存储，但确认仍必须代表收到的完整快照。

## 7. 恢复留给应用

本版无resume(checkpoint)、进程崩溃后自动续跑、exactly-once或工具幂等数据库。

IntentRecorded只能证明“派发意图已确认”，崩溃时可能没派发，也可能动作已完成但结果未写入。不能把它简单当成Pending重新执行。外部恢复应先查询副作用、人工确认或使用工具幂等键，再按权限与模型协议修复历史。

检查点还可能包含图片、签名、提示词和业务敏感数据；外部实现必须处理访问控制、加密、保留和删除。不要把它放进UI journal，也不要默认永久写入Memory。


终态确认丢失也有歧义：外部数据库可能已写Completed快照，Core却因未收到确认返回Failed并标记checkpoint错误。协议不伪装两边一定一致；恢复/核查必须查实际提交状态，不能据此再次执行动作。
