# v0.3：通用底座的边界与本次取舍

## 1. 目标不变

本项目是可嵌入、可定制的 Agent 执行底座，不是 Mona 的 Rust 重写，也不是一个完整聊天平台。Mona 只是检查通用接口缺口的真实案例，不能由它的业务功能清单决定 Core 的功能清单。

不存在所有项目都必须遵守的统一“Agent 内核行业标准”。本次纳入的是在多种执行框架中可找到同类需求、且不依赖特定业务的协议与控制边界；具体 API 是本项目的工程选择，不宣称兼容上游。参考依据见[来源](REFERENCES.md)。

纳入条件：跨业务可用；只有执行器在正确时点接入才可靠；不捆绑数据库/界面/厂商产品；不安装扩展时默认路径仍能工作。

## 2. 四项纳入，分别只补到接口层和必要执行层

| 需求 | API/Core 本次承担 | 外部实现继续承担 |
|---|---|---|
| 多模态和结构化结果 | 内容块、工具成功/已知错误、模型传递、验证与大小限制 | 图片采集/压缩/上传、PDF解析、Office截图、文件读取和授权 |
| 按任务/轮次选择工具 | Run 工具上限、串行选择管道、模型可见集合与实际执行集合一致 | 用户订阅判断、Mona能力组、Skills路由、MCP工具发现 |
| 可靠执行记录 | 可等待的检查点、不可变快照、提交次序、失败停止和结算状态 | 存储事务、加密、账号隔离、聊天Session、恢复/审批策略 |
| 模型协议与参数 | 通用选项、私有回传载荷、调用关联、预算/审计不被绕开 | 厂商适配、凭据刷新、端点、模型权限、兼容性转换 |

没有加入 Memory 数据库、Planner 调度器、Office、浏览器、代码编辑器、渠道、Python FFI/RPC、完整 thread/session、多 Agent 工作流、企业权限体系、JEV 或新的决策引擎。

## 3. 为什么检查点不是“把持久化产品塞进 Core”

UI事件可以丢。插件在结束事件里写一次数据库，无法阻止“工具已经执行，关键记录还没保存”的竞态。

因此只有提交位置和失败语义由 Core 拥有，存储由一个可选 CheckpointSink 提供。默认不安装 sink，没有磁盘或数据库依赖。内存 sink 的成功只说明内存接纳；真正的耐久性由外部 sink 明确承诺并验证。

CheckpointSink 不是任意业务事务回调。不要把扣款或审批动作塞进 commit；它应记录运行快照。记忆提取仍属于 Memory 插件，不能把整个执行记录默认当成永久用户画像。

## 4. 为什么工具选择不是热加载

Host 注册表仍在启动完成后冻结。RunRequest.allowed_tools 给出可信上限；ToolSelector 每轮从上限内筛选。这足以支持预注册能力的按需暴露，不需要引入插件包管理和任意修改运行状态的 Hook。

同轮多个选择器只能继续收紧。下一轮从 Run 上限重新开始，允许根据新的执行结果激活此前隐藏但已注册的工具。参数校验、权限否决和副作用最终授权仍必经；“模型没看到”也不能替代实际执行校验。

未注册的 MCP 新工具、插件热更新、改变租户权限域，仍由外部发现/装配/重建 Host 策略处理。本版不在运行时修改工具实现或 Schema。

## 5. 为什么不添加完整“思考UI”

保留模型要求回传的签名、缓存块等私有数据，是通信正确性；让用户看见进度解释，是产品展示。这两件事不能混为一谈。

本版把私有协议字段保留在可信模型消息、规范化审计和检查点内，不发给 UI。可公开的进度说明可使用已有文本/工具事件；没有解析、要求、生成或展示模型隐藏思维链的新功能。

## 6. 当前 Mona 迁移仍需做什么

- 将原有 Python 执行器入口映射到公共 AgentRuntime/AgentExecutor；复用旧工具需要 Python 绑定或 RPC，这不是现有 UI bridge 的功能。
- 会话/工作区/附件先在 Mona 的可信应用层解析，再构造 RunRequest。原有聊天、工作流、子 Agent、审批继续由 Mona 管理。
- 将工具输出映射为 ToolOutput，明确 is_error、富内容和取消/未知结果，不能把所有错误当作成功字符串。
- 将能力组规则实现为 ToolSelector；把已有存储实现为 CheckpointSink，并说明事务与恢复规则。
- 继续迁移 Provider、事件兼容、业务脱敏；新 Core 不自动兼容原 WebSocket 协议。

**因此，v0.3 补的是通用契约，不是“已完成 Mona 无损替换”。**真实集成前仍需 Rust 编译验收和功能不退化测试。
